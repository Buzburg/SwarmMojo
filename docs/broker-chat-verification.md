# Project memory in broker chat

The broker now prepares project context through the established ROMS MCP `memory_prepare_context` tool before generation. Both synchronous and asynchronous dispatch use the same preparation/answer validation. Plain chat keeps its previous request and text-result contract; adding a project ID explicitly requests scoped evidence and returns the answer plus its context receipt.

The memory process is owned and reaped through the existing timeout/cancellation boundary. Discovery checks the fixed tool schema; arbitrary tool names are never accepted. The decoder validates scope, selection counts, warning labels and caller-supplied verification outcomes. Existing ROMS correction, retraction, expiry and revision filters remain authoritative. No chat response creates a verified memory or promotes a candidate.

Model input uses quoted source-bearing summaries in the user message, separate from trusted instructions. Full receipts remain in the response, including source/record IDs, revision, expiry, caller-supplied evidence, omission counts and selection status. This is a prompt boundary, not proof that the model resists every prompt injection. Retrieved content grants no execution permission.

Project prompts are at most 4096 UTF-8 bytes; only the first 500 characters are used as the keyword query. ROMS context is at most 2048 characters and its rendered evidence view at most 8192 bytes. This is a size budget, not an exact tokenizer budget for every possible input; the runtime still enforces its context limit. The gateway skips its unscoped document/skill lookup for these requests and removes this gateway-only option before forwarding. Imported-document semantic retrieval is not yet scoped into this path.

Project generation uses temperature zero, no prompt cache, at most 512 tokens, and a native JSON schema for one answer string of at most 1600 characters. The broker independently validates the result, including duplicate keys, exact fields, length and successful stopping. The ordinary chat sampler/template and installed model/runtime binaries are unchanged.

## Actual evidence

Sixty-three focused tests passed: project context and answer boundaries, existing broker actions/admission, real MCP lifecycle, actual broker disconnect cleanup, gateway TCP cancellation and build readiness. The compiled broker sends actual isolated ROMS records to a controlled HTTP endpoint, returning matching receipts without changing the fixture database. A separate socket test disconnects project chat while its MCP child is running, verifies responsive ping and waits for that child to disappear.

Two opt-in live trials then passed through the compiled broker, an isolated instance of the actual gateway application and the installed 2.9B model. Each trial introduced a fresh random deployment code into a temporary verified lesson. Both answers contained the corresponding value and stopped normally; the database remained unchanged. The gateway's unscoped retrieval function was replaced with a failing assertion, proving it was not used. Full traces are saved in the parent workspace at `deployment/broker-grounding-live.json`. Fixture verification receipts are explicitly simulated, not claimed as real external evidence.

Earlier unconstrained runs failed: blank text, an invented code sample/tool call, and repeated tool-output markup exhausting 512 tokens. One earlier successful reply did not reproduce across fresh trials. Concise rendering alone did not solve this. Runtime schema-constrained generation resolved the two final checks; those narrow checks do not establish broad factual reliability or prompt-injection resistance. The failures remain part of the evidence, rather than being replaced with a blanket quality claim.

The schema syntax was confirmed against the pinned runtime's `tools/server/README.md`, matching the upstream [server interface documentation](https://github.com/ggml-org/llama.cpp/blob/46847e61582097979f539595d893d83d8e1d1af1/tools/server/README.md). Required live verification now includes both fixture trials when `verify_all.py --drafts` is selected with explicit live-model opt-in.

After service activation, the installed check with the existing empty `omarchy-build` scope exposed another incomplete model response. Empty evidence now returns a deterministic no-usable-memory notice without model invocation, explicitly marked `generated: false`; successful model replies are marked `generated: true`. Forty-one focused chat/action/admission tests passed after this change. This is a deliberate no-evidence branch, not a fabricated model answer. The installed service then passed the read-only empty-scope check; both the initial failure and final result are saved as `deployment/broker-grounding-installed-initial.json` and `deployment/broker-grounding-installed.json`. No synthetic verified records were inserted into the user's database.

Direct Mojo/C conversation dispatch, saved turns/checkpoints, full memory integration and the broader PDF roadmap remain open. This increment still generates through the installed authenticated HTTP model path. Training and 7.2B loading remain deferred.
